## What it is

One crate, three jobs, each chosen because the failure it prevents is a bug report a week after the
fact rather than a crash at the scene:

1. **Pipeline cache** — read, validate, repair, append `shader_environment` records. Byte-compatible
   with your existing format (`yuzuvkch`, version 1, 16-byte keys), so an existing user's shaders load
   without a rebuild and both implementations can read the same file.
2. **Content selection** — which update and DLC actually load, by title version.
3. **An AArch64 translator** — decoder, block analysis, reference interpreter, x86-64 encoder, and an
   address-keyed runtime with a guest-memory guard.

There is no HLE service layer and no Vulkan backend. Those are the two places where being in Rust buys
nothing until a booting core exists, and they are yours to keep.

## Why the first two

Both started as defects in your tree at `c3aa70f`, and both are still there:

- `RegisteredCache::ProcessFiles` keys metadata on title id, which is identical at every version of a
  patch, and fills it with `insert_or_assign`. **Whichever CNMT the directory walk reached last wins**,
  and directory order is filesystem order — so with two updates installed, the ordinary case, the game
  boots an arbitrary version. `GetEntryVersion` then reports that same arbitrary number.
- `LoadPipelines` wraps the whole read loop in one `try` whose handler deletes the cache file, while
  records ahead of the damage have already been applied. The emulator resumes half-populated with no
  file on disk.

Neither is fixed here. The crate's cache module is a working implementation of the behaviour they
should have, with the repair path exercised: keep every record that parsed, drop the damaged tail,
rewrite the file, never delete a user's shaders over one bad record.

## What is measured, and how

Every number below is reproducible from a clean clone with one command, and the instruments are named
because a number without its instrument is a rumour:

| claim | instrument | result |
|---|---|---|
| decoder covers real compiler output | `llvm-mc` | 304/304 instructions in four clang-generated `.text` blobs (`-O0`, `-O2`, `-Os`) |
| interpreter is correct | `qemu-aarch64` differential | 18/18 programs, FP included |
| encoder is byte-exact | `llvm-mc` | 47/47 forms |
| compiled code matches the interpreter | same programs, both engines | registers, FP file and flags agree |
| a pipeline cache is worth having | two processes, Mesa disk cache off | 0.260 ms cold → 0.003 ms from a saved blob on a 9070 XT (~87×); 0.241 → 0.003 on an MI25; 0.243 → 0.003 on a Vega FE. Blob ~18 KB |
| speed, both halves | `examples/bench` | **1.87× faster** than the interpreter on a loop; **0.53× — slower — on a single-use straight-line block**, because driver overhead dominates |

That last row is the one I would want a maintainer to read twice. It is not a sales claim: the JIT pays
on loops and loses on code that runs once, and any adoption decision should assume both halves.

One more, because it argues for the module more than any speed number: **a Vulkan driver will not
reject a corrupt pipeline cache blob.** It returns `VK_SUCCESS` and silently ignores it. So the format
has to be validated by the caller, and damage repaired rather than refetched. That is why the cache
module is not a nice-to-have in the design.

## How it plugs in

- **C ABI**: `include/vitrine.h`, with `libvitrine.a` or `.so` from `cargo build --release`.
- **CMake**: `find_package(vitrine 0.1 CONFIG REQUIRED)` → `vitrine::vitrine`.
- **Your CPU backend**: `cpp/citron/arm_vitrine_64.{h,cpp}` implements `Core::ArmInterface`, compiled
  and tested against a copy of your own declarations from `c3aa70f` (with `ThreadContext`'s `0x320`
  layout pinned by `static_assert`).
- **The integration steps, including the ones that bite**: `cpp/citron/INTEGRATION.md`.

## What I did not do, so the review starts from the right place

- **It has never been compiled inside Citron.** The backend is tested against a faithful shim of your
  headers, not against your build. Expect signature fixes on the first real compile.
- **No LL/SC, no SIMD/NEON, no AArch32, no MMU in the JIT's memory model.** A game will not run on
  this today. It is a translator and a cache, not a core.
- **No KThread context** in the adapter yet, and `DataAbort` stops rather than raising.
- I did not touch your tree, and I am not asking you to adopt anything on faith: `./build.sh` runs the
  full suite, both C++ checks and the CMake package test in one command, and CI does the same on every
  push.
